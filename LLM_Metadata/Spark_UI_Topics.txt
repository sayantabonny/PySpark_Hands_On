Spark UI: observe the code you just ran
======================================
Use a relevant checkpoint, not a full UI tour. There are no levels, scores or lab-completion requirements.
The LLM must warn before moving past an important observation, including when it wrote a delegated step.
Give one navigation move and ask for one metric or observation at a time. Wait for the learner's response.
The learner can explicitly skip the UI checkpoint. Do not silently skip it on their behalf.

Where to look
- Jobs: action/preparation work, associated stages and timing.
- Stages: task count, median/max duration, input and shuffle distribution, spill and failures.
- SQL / DataFrame: executed physical plan, scans, Exchange, Window/joins and adaptive changes.
- Storage: cached partitions, fraction materialized, storage level and memory/disk footprint.
- Executors: resource/work distribution, CPU/GC and failures; local mode is not a multi-node cluster.
- Environment: recorded settings; confirm current runtime SQL settings in the session when necessary.

Important distinctions
- DataFrame row processing is lazy, but reads may trigger preparatory jobs for file discovery or schema inference
  BEFORE a DataFrame action. Transformations do not usually execute rows; they do not guarantee an empty Jobs tab.
- A task attempt processes a stage partition; retries/speculation can add attempts. Four cores limit concurrent tasks,
  not total task count. File count, input partitions and shuffle/output partitions need not match.
- SQL executions, plan nodes, AQE query stages, scheduler stages and codegen groups have different IDs.
  IDs can change across runs. Identify work by action, time, target path/table and plan, then use that run's links.
- Shuffle can be local. Skipped/reused stages are not failed stages. Verify the reason from actual execution evidence.
- Estimates, stored cache bytes, source bytes, rows and shuffle bytes measure different things.

Checkpoint menu — choose only what the current code makes relevant

1. Input and lazy execution
   After reading: inspect any file-listing/inference job. Distinguish preparation from row processing.
   On the first action: inspect the new query/job and input volume. Do not promise a fixed number of jobs.

2. Caching
   Before materialization: cache() requests reuse; Storage may still be empty.
   After the first full action: check cached fraction/partitions; on reuse inspect InMemoryTableScan and scan work.
   Observe before unpersisting, replacing the DataFrame or restarting the kernel. Delta snapshot metadata is not cached business rows.

3. Shuffle, windows and aggregation
   After a relevant action: follow scan -> Exchange -> downstream operator in the plan.
   Read partitioning, actual read tasks and Shuffle Read/Write; correlate the operator with the scheduler stage.
   WholeStageCodegen groups are not scheduler stages. A transformation alone may not yet have an executed UI plan.

4. Partitions, AQE and output files
   Compare one controlled setting change: initial/final plan, AQEShuffleRead if present, task distribution and duration.
   Record the actual setting; do not assume the shuffle-partition count defaults to 200 in every environment.
   Compare active files in the specific Delta snapshots, not every physical file still on disk.

5. Joins and skew
   Check actual broadcast hash/sort-merge/shuffled hash strategy and cardinality before tuning.
   Compare median/max duration and bytes before blaming skew; verify build-side size, broadcast cost and AQE behavior.
   Try a suitable change only after forming a hypothesis; validate identical business results.

6. Scans and pruning
   Inspect ReadSchema, PartitionFilters, PushedFilters and file/byte metrics where supported.
   Distinguish column/predicate/static partition pruning, data skipping and dynamic partition pruning.
   DPP needs an appropriate partitioned join; do not claim every filter is pushed down.

7. Memory, resources and errors
   Use relevant task/executor CPU, runtime, GC, serialization, peak-memory and spill metrics plus the first useful error/log.
   Distinguish driver vs executor and execution vs storage pressure. Spilling is not itself a failure.
   Optional failure experiments must use bounded inputs in an isolated, heap-capped process with a restore path.
   Driver memory is a process startup setting; spark.stop()/a new builder alone does not reliably change its JVM heap.

8. Engine choices and unfamiliar diagnosis
   Recognize Python execution boundaries vs native expressions, Catalyst optimization and fused codegen groups.
   Consult generated-code/Tungsten details only when they explain a real observation.
   State a symptom, cite evidence, change one variable, and verify the result. A rejected hypothesis is useful learning.

UI handoff wording
"UI checkpoint: [what this step may have changed]. Open [tab/action]; report [one observation]."
Flag before the action when preparation is needed; inspect after it. Do not add another coding task while this
checkpoint is pending. If the UI is inaccessible, report the limitation and let the learner explicitly defer it.
