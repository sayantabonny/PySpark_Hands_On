Hands-on PySpark practice map
===========================
Goal: build working pipelines and think through their design as a data architect.
Use one lane and one small problem at a time. This is a menu, not a completion checklist.
No pass quotas, grades, API memorization or obligation to work through every reference entry.

1. Read trustworthy inputs
   - Read JSON/CSV/Parquet/Delta with an appropriate schema; separate malformed input from valid data.
   - Preserve lineage and useful ingestion metadata; reason about inference, schema drift and safe conversion.
   - Reconcile file/row counts and define what to quarantine, reject or accept.
   Architect lens: what is the source contract, and what must remain replayable?
   UI: file discovery vs scanning; cache materialization and scan pruning.

2. Transform and validate
   - Select/derive/filter columns using sound conditional and null logic; clean and parse only what is required.
   - Aggregate/profile at the correct grain; use meaningful quality rules, thresholds and exception evidence.
   - Pivot/unpivot or choose SQL/DataFrame expressions when the business output needs reshaping.
   Architect lens: what does one row mean before and after this step?
   UI: narrow work vs aggregate shuffle; column pruning and native expressions.

3. Handle time correctly
   - Parse timestamps/epochs with explicit assumptions, invalid-data handling and required precision.
   - Distinguish an instant from time-zone rendering; validate UTC/local display and daylight-saving ambiguity where relevant.
   - Implement only the calendar boundaries, intervals or YoY/MoM comparisons required by the problem.
   Architect lens: is this commit time, arrival time or business-effective time?
   Reference only: exhaustive date extractors, formatting tokens and function signatures.

4. Relate and reconcile datasets
   - Choose joins and keys; preserve unmatched rows, handle null keys, predict fan-out and check referential integrity.
   - Distinguish duplicate deliveries, exact duplicates and competing versions; define deterministic winners.
   - Combine/compare compatible datasets with correct positional/by-name and distinct/multiset semantics.
   Architect lens: what relationship and cardinality are assumed, and how will we prove them?
   UI: broadcast vs shuffle join, skew and data movement.

5. Work with ordered and nested data
   - Use windows for ranking, previous/next events and running/rolling values with deliberate frames and tie behavior.
   - Derive event sequences, gaps, sessions or Top-N when needed.
   - Access/transform arrays, structs, maps and nested JSON; control null/empty behavior, ordering and explode cardinality.
   Architect lens: are we changing event order, time meaning or row grain?
   UI: Exchange, Sort and Window; connect the physical plan to actual stages.

6. Model change and history — current focus: FP-003
   - Build current state or historical versions from CDC, including deletes, no-change updates and late events.
   - Design replay-safe incremental boundaries and idempotent processing; verify a rebuild gives the same business result.
   - Model business/surrogate keys and fact/dimension relationships, including effective-dated joins and late dimensions.
   Architect lens: what is the temporal contract, and how does recovery work after partial failure?
   Reference: SCD3/SCD4, star/snowflake and Data Vault trade-offs; implement specialized models only when useful.

7. Deliver reliable Delta tables
   - Write and mutate tables with clear path/catalog identity, schema rules and MERGE/update/delete behavior.
   - Understand version history, concurrency and retention; verify recovery and VACUUM implications.
   - Improve file layout, compaction, statistics, pruning and data skipping from measured workload evidence.
   Architect lens: what correctness and recovery guarantees do downstream consumers need?
   Reference: generated/identity columns, constraints, cloning, ZORDER/clustering and platform-specific options.

8. Reason about execution and cost
   - Choose partitions and native vs UDF processing from actual data volume, distribution and observed execution.
   - Bound driver data and reason about serialization, retry-safe partition writes and broadcast/accumulator semantics.
   - Diagnose shuffle, skew, cache, spill and small files; change one variable and verify correctness and benefit.
   Architect lens: which resource or data-distribution assumption limits the design?
   Reference: foreachPartition/mapPartitions, Pandas UDF/Arrow, accumulator APIs and engine internals as needed.

How to use this map
- A coding sub-problem normally needs 1–2 meaningful lines/statements; split longer work instead of code-golfing.
- Use documentation/AI for syntax. Ask for a hint, "do this one", "skip" or "next" freely.
- Skipping means the LLM supplies the small runnable step and its effect, then continues when you are ready.
- Before moving on, the LLM must flag a relevant UI observation, especially after an action, cache, shuffle or write.
- Favor a one-sentence architectural decision tied to the code over a separate quiz or long design essay.
- The detailed catalogue remains at archive/reference/Primary_Topics.txt. It expands this map; it is not extra homework.
